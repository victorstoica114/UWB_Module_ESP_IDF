# Passive DS-TWR ESP32 Solver Experiments — 2026-08-01

This directory preserves the first receive-only Passive DS-TWR implementation
that performs the complete position calculation on the ESP32-S3 tag. The
Raspberry Pi dashboard only receives and displays finished position and anchor
geometry telemetry.

## Current reference

The current radio schedule uses a five-packet multipoint Full-DS exchange
(`N + 2` for four anchors): one broadcast POLL, three delayed RESP packets and
one aggregate FINAL. Two consecutive, non-overlapping radio stars provide six
raw passive observations to each position solve. No temporal position filter
is used.

The `nplus2_dual_star_stable_stackfix_45s` capture is the stable checkpoint:

- 3,363 raw positions in 45.07 s (74.6 positions/s)
- X/Y standard deviation: 1.48/1.53 cm
- RMSE from the surveyed centre: 2.66 cm
- P95 error from the surveyed centre: 4.54 cm
- solver queue drops: 0
- nominal measurement window: 12 ms

The reference geometry is a surveyed 3 m square with the receive-only tag at
its centre (1.5 m, 1.5 m). The firmware reports `position_filter=none` and
`solver_location=esp32_tag` for every captured position.

## Design basis

The listener estimator follows the double-sided timing formulation described
in *Precise Ranging: Modeling Bias and Variance of Double-Sided Two-Way
Ranging with TDoA Extraction under Multipath and NLOS Effects* (Rathje and
Landsiedel, 2024). Symmetric response timing is retained and same-star
observation correlation is represented by a compact spatial GLS weight. This
is measurement covariance weighting, not temporal filtering.

The multipoint schedule reduces a four-anchor exchange from twelve separate
POLL/RESP/FINAL packets to five packets while keeping the tag strictly
receive-only. Delayed TX deadlines are generated by the DW3000; no absolute
tag/anchor clock synchronization or CFO correction is used by the passive
double-sided estimator.

## Reproducibility

Each `.jsonl` capture contains the raw positions and anchor ranges. Its paired
`.metadata.json` records the runtime configuration and firmware status, while
the optional `.logs.jsonl` file records radio and solver diagnostics. Earlier
captures are intentionally retained, including rejected timing and covariance
experiments, so that later conclusions can be reproduced without rebuilding
historical firmware.
